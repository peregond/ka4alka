# Обновление существующего Sites из GitHub

Исходники: `peregond/ka4alka`, ветка `claude/quirky-hopper-1vlmj6`, каталог `web-index/`.
Публикация: https://ka4alka-online-new.peregon.chatgpt.site/.
Текущий проект: `appgprj_6ac6006f8d248191acac74b581afe7ba`, привязка D1 `DB`.

GitHub Actions **Prepare verified Sites source** запускается для каждого коммита этой ветки, чтобы у автоматизации Sites всегда был проверенный HEAD, даже после изменений только Windows-приложения. Он устанавливает зависимости по lockfile, проверяет метаданные, поиск раздач, TypeScript и сборку Sites. После успешной сборки создаёт артефакт `sites-source-<полный SHA>` с ZIP исходников и `source-manifest.json`. ZIP содержит корень сайта, включая `.openai/hosting.json`; папки `web-index/` внутри ZIP нет. Архив берётся из проверенного коммита, а не из рабочей папки. Секреты, локальная база и результаты сборки в него не входят.

`source-manifest.json` также содержит `sourceFiles`: SHA-256 каждого файла. Перед тестами в Sites выполните `node scripts/verify-source.mjs /путь/к/source-manifest.json` из корня сайта. Проверяется фактическая рабочая папка, а не только ZIP. Если файлы отличаются, восстановите их из того же архива целиком; не смешивайте старые `lib/catalog-source.ts`, `lib/tvdb-title.ts` и новые тесты. GitHub CI теперь проверяет и собирает именно распакованный архив публикации.

`source-manifest.json` содержит полный коммит, хэш дерева `web-index/`, идентификатор существующего проекта, имя DB и SHA-256 архива. Хэш дерева позволяет пропускать коммиты, которые меняют только Windows-приложение. Срок хранения артефактов — 30 дней; после этого исходники можно получить из указанного коммита GitHub и повторить проверки.

**GitHub workflow подготавливает исходники; он не публикует Sites.** Для публикации нужна задача ChatGPT с доступом к GitHub и существующему Sites-проекту. OpenAI не документирует прямой автодеплой Sites из GitHub Actions. Одного изменения hosting.json недостаточно для выдачи доступа или создания расписания.

## Однократное подключение в чате существующего сайта

Передать следующий запрос в чат проекта Sites:

```text
Настрой обновление существующего сайта https://ka4alka-online-new.peregon.chatgpt.site/ из GitHub.

Репозиторий peregond/ka4alka, ветка claude/quirky-hopper-1vlmj6, исходники сайта в web-index/. Используй distribution/SITES-GITHUB-UPDATE.md как описание процесса.

Сначала проверь, что открытый проект действительно имеет ID appgprj_6ac6006f8d248191acac74b581afe7ba. Сохрани этот проект, существующую базу D1, DB, секреты, домен и настройки доступа. Не создавай новый проект и не копируй hosting.json старого сайта. Проверь доступ к GitHub. Если здесь невозможно читать репозиторий или создавать автоматизацию, сообщи конкретно недоступную возможность.

Сравни текущие исходники Sites с web-index/ выбранной ветки. Изменения, которые есть только на Sites, сначала покажи отдельным списком и подготовь их перенос в GitHub, чтобы они не были потеряны при переходе. После согласования единого исходника используй GitHub для дальнейших изменений сайта.

Для публикации проверь текущий HEAD указанной ветки и выбирай его только с успешным запуском Prepare verified Sites source. Если проверка ещё идёт или упала, не заменяй HEAD произвольно выбранным старым коммитом: оставь действующую публикацию и сообщи статус. Используй соответствующий артефакт sites-source-<SHA> или получи web-index/ прямо из этого точного коммита. Проверь source-manifest.json, SHA-256 архива и ID проекта. Исходники web-index/ соответствуют корню сайта.

Перед проверками замени исходники корня сайта содержимым проверенного ZIP: не оставляй старые версии файлов и не накладывай старые исходники поверх новых. Сохрани секреты, D1, DB и настройки публикации; эти данные не входят в архив. Выполни node scripts/verify-source.mjs /путь/к/source-manifest.json — все sourceFiles должны совпасть. Если проверка показывает Changed или Missing, восстанови перечисленные файлы из этого же архива до запуска тестов.

Выполни node tests/title-lookup.mjs, node tests/title-identity.mjs, node tests/release-performance.mjs, tsc --noEmit и npm run build. Если проверка не прошла, оставь текущую публикацию. При успехе сохрани версию с точным Git-коммитом и опубликуй в существующий сайт. Применяй только новые добавочные SQL-миграции: 0001_title_metadata.sql создаёт кэш метаданных, не пересоздаёт D1 и существующие таблицы. Проверь публичные /api/health, /api/catalog и /api/title для tt1160419 (movies) и tt8910922 (series), а также /api/releases для реальной карточки из каталога.

Затем, если Sites Automations доступны, создай облачную задачу раз в 30 минут: проверять эту ветку, пропускать уже опубликованное дерево web-index/, ждать успешного Prepare verified Sites source и выполнять тот же цикл проверок и публикации. Задача должна иметь собственный доступ к GitHub и Sites; не полагайся на подключение посетителей сайта. Не допускай одновременных публикаций. Сохраняй последний успешно опубликованный коммит и sourceTree в истории задачи, обновляя их только после успешной публикации. Если появится новый коммит во время сборки, закончи публикацию проверенного SHA и оставь новый для следующего запуска.

Не печатай и не копируй секреты. Не меняй main, не создавай PR. В ответе раздели: что опубликовано сейчас, создана ли автоматизация, её расписание и что осталось недоступным. Не называй автопубликацию включённой без реально созданной задачи.
```

## Статус настройки

- Привязка исходников обновлена со старого проекта на существующий новый проект, ранее указанный владельцем.
- GitHub workflow проверяет и подготавливает исходники.
- Доступ задачи к Sites и создание расписания выполняются в Sites; из облачной среды без инструмента Sites эти действия недоступны.

Документация OpenAI: https://developers.openai.com/codex/sites#understand-projects-versions-and-deployments и https://help.openai.com/en/articles/20001339-creating-and-using-chatgpt-sites (Schedule updates to a Site).
