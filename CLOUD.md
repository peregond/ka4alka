# Работа с проектом в Codex Cloud

Репозиторий: `peregond/ka4alka`, ветка `main`.

- `native/` — приложение Windows, C# / WPF, .NET 10 и MonoTorrent.
- `tests/` — исходники интеграционных проверок нативного приложения.
- `lan-core/` и `lan-tests/` — протокол локальной сети и его независимые от WPF проверки.
- `web-index/` — сайт «Ка4алка Онл@йн», TypeScript, React, Next/Vinext и Cloudflare D1.
- `distribution/` — описание распространения, протокола обновления и заметки к опубликованным бинарным релизам.
- `build.ps1` и `package-release.ps1` — сборка Windows-приложения и подготовка релиза.

Исходники можно редактировать в облачной среде. Полный запуск WPF-приложения, UI-проверки и тесты, которым нужна Windows Desktop Runtime, выполняются на Windows; Linux-среда не заменяет эти проверки. Для кросс-компиляции на Linux требуется .NET 10 SDK и свойство `EnableWindowsTargeting=true` при сборке проекта. Не отмечайте Windows-проверки выполненными, если они не запускались.

Перед продолжением разработки сверяйте выбранную ветку с последним опубликованным тегом GitHub Release: релизы могут выходить из отдельных веток раньше обновления `main`. Используйте существующий изолированный checkout; дополнительный worktree создаётся только по явному запросу пользователя. Подготовка релиза включает нативные Windows-проверки, проверку подписи пакета, обновление из ранее опубликованной версии и проверку публичной доставки компонентов.

Для 0.39.0 рабочая ветка — `codex/lan-downloads-0.39.0`; исходная опубликованная версия — 0.38.0. Сначала выполните `dotnet run --project lan-tests/Kachalka.LanTests.csproj -c Release`: эти проверки работают и на Linux. Они должны проверять настоящее защищённое соединение между локальными экземплярами, сопряжение с подтверждением на обеих сторонах, отказ неизвестным устройствам, передачу magnet и `.torrent`, отзыв доверия и повторную отправку без дублирования очереди. Linux-проверки не заменяют Windows-интеграцию, интерфейс сопряжения и получение задания в настоящую очередь приложения.

На Windows проверьте новые экраны устройств в обеих темах и узком окне, передачу задания в настроенную папку получателя, а также прежние масштабирование, навигацию, все четыре полки каталога и действия загрузок. `WindowsUpdateSmoke.ps1` запускает проверки LAN-протокола до прежних интеграционных и UI-проверок. Затем запустите workflow `Prepare signed Windows release` с версией `0.39.0`: он готовит только черновик. Перед публикацией проверьте снимки экрана, подпись, контрольные суммы и обновление с опубликованной 0.38.0; после публикации отдельно проверьте публичный установщик и получение изменившихся компонентов.

В `web-index/` зависимости устанавливаются по `package-lock.json`; требуется Node.js не ниже 22.13. Перед изменением сайта ознакомьтесь с его `README.md` и скриптами `package.json`. Рабочие значения секретов и привязки сервисов в облачной среде настраиваются отдельно и не входят в Git.

В Git не включаются `node_modules`, `dist`, `.tools`, результаты тестов, локальные профили инструментов, `.env`, ключи и кэши. Файлы `web-index/public/posters/` — подготовленные статические изображения сайта, а не локальный кэш пользователя. `web-index/build/` содержит исходник плагина сборки и его лицензию.

История сайта перенесена как предыстория общего проекта. В её экспортированной копии исключён ранее отслеживавшийся `tsconfig.tsbuildinfo`. Оригинальная история и Git-метаданные остаются локально в игнорируемом каталоге `.tools/github-migration/`.
